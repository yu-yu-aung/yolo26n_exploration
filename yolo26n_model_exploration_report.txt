YOLO26n MODEL EXPLORATION
Technical Investigation Report
Date: 14 October 2026

============================================================
1. PURPOSE AND SCOPE
============================================================

The purpose of this investigation was to inspect a pretrained YOLO26n object-detection model using Python, PyTorch, and Ultralytics. The focus was on understanding the model's architecture, input and output tensors, layer connections, learned parameters, configuration settings, detection head, and training loss implementation.

This was an inspection of an existing checkpoint, not a project to train a new model from scratch. The checkpoint's architecture and stored weights could be inspected directly. However, configuration defaults displayed by the installed Ultralytics package should not be mistaken for the exact historical settings used to train this particular checkpoint.

Model file:
    models/yolo26n.pt

Model class:
    ultralytics.nn.tasks.DetectionModel

Task:
    Object detection

============================================================
2. MODEL OVERVIEW
============================================================

The inspected model is YOLO26n, a small object-detection model. Its main components can be understood as:

1. Backbone: extracts visual features from the input image. (from layer 0 - 10)
2. Neck: combines feature maps at different spatial resolutions. (from layer 11 - 22)
3. Detection head: predicts bounding boxes and class scores at multiple scales. (layer 23)

The inspected top-level layer types included:

- Conv
- C3k2
- SPPF
- C2PSA
- Upsample
- Concat
- Detect

The model contains 2,572,280 parameters in total. The loaded checkpoint's parameters were not trainable in the inspection setup, so the reported trainable parameter count was zero. This does not mean the architecture is inherently unable to train; it reflects the loaded model's current parameter settings.

============================================================
4. UNDERSTANDING THE LAYERS AND CONNECTIONS
============================================================

Conv:
    Applies a convolution to extract features. The inspected Conv blocks
    include convolution, BatchNorm, and SiLU activation components.

C3k2:
    A feature-processing block used repeatedly in the network.

SPPF:
    Spatial Pyramid Pooling - Fast. It expands the model's contextual
    view of features through spatial pooling.

C2PSA:
    A feature-processing block that uses attention-related operations.

Upsample:
    Increases the spatial dimensions of a feature map. This operation
    does not itself contain learned parameters.

Concat:
    Joins feature maps along a tensor dimension. The inspected Concat
    layers have no learned parameters of their own.

Detect:
    Produces object-detection predictions from feature maps at multiple
    resolutions.

The model's "from" connections show which earlier layer outputs are
used by later layers. In particular, the neck combines upsampled features
with features from earlier layers, then processes the combined features.
This allows information from different spatial resolutions to contribute
to detection.

Layers 11, 12, 14, 15, 18, and 21 had zero parameters in the inspection.
This is expected for the Upsample and Concat operations.

5. LEARNED PARAMETERS AND WEIGHTS
============================================================

The layer-inspection script printed parameter names, shapes, parameter
counts, and selected values rather than dumping every value in the
checkpoint.

For example, the first convolution's weight tensor had shape:

    [16, 3, 3, 3]

Its parameter count is:

    16 * 3 * 3 * 3 = 432

The first Conv block also included BatchNorm parameters. Its total
parameter count was 464:

- Convolution weights: 432
- BatchNorm weight: 16
- BatchNorm bias: 16

The inspected convolution used a 3 x 3 kernel, stride 2, and padding 1.
The Conv block included BatchNorm and SiLU activation.

The investigation also inspected BatchNorm settings such as epsilon
and momentum, along with selected convolution weights and BatchNorm
values. These values are learned or stored model parameters; they are
different from settings such as kernel size and stride, which define
how an operation is performed.

The full model parameter count was:

    2,572,280 parameters

============================================================
7. DETECTION HEAD AND OUTPUT
============================================================

The Detect layer takes feature maps from:

    [16, 19, 22]

These feature maps correspond to three spatial resolutions:

    80 x 80
    40 x 40
    20 x 20

Their total number of prediction locations is:

    80 * 80 + 40 * 40 + 20 * 20
    = 6400 + 1600 + 400
    = 8400

The detection head reported:

    nc = 80
    nl = 3
    reg_max = 1
    no = 84
    stride = [8, 16, 32]
    end2end = False

The main prediction tensor had shape:

    [1, 84, 8400]

For this model configuration, the 84 channels are consistent with:

    4 box-regression values + 80 class scores = 84

The tensor therefore contains 84 output values for each of 8,400
prediction locations, for a batch of one image. The precise decoding
and post-processing of these predictions is a separate step.

The Detect layer also contained the following submodules:

    cv2
    cv3
    dfl = Identity
    one2one_cv2
    one2one_cv3

The presence of one-to-one prediction branches is relevant to the
end-to-end loss criterion described in the next section.

============================================================
8. LOSS FUNCTION IMPLEMENTATION
============================================================

The model's init_criterion() method contained the following decision:

    return E2ELoss(self) if getattr(
        self.model[-1], "one2one_cv2", None
    ) is not None else v8DetectionLoss(self)

Because the inspected detection head had a one2one_cv2 module, the
criterion selected for this model was:

    ultralytics.utils.loss.E2ELoss

Inspecting the E2ELoss source showed that it creates two v8DetectionLoss
instances:

    one2many = loss_fn(model, tal_topk=10)
    one2one = loss_fn(model, tal_topk=7, tal_topk2=1)

The criterion separates the predictions into "one2many" and "one2one"
branches, calculates a loss for each branch, and combines the two
loss values with weights.

The inspected implementation initialized these values:

    total = 1.0
    o2m = 0.8
    o2o = total - o2m
    final_o2m = 0.1

Its combined loss was:

    combined_loss = loss_one2many * o2m
                  + loss_one2one * o2o

Thus, the initial weighting was 0.8 for one-to-many and 0.2 for
one-to-one. The weights are not fixed: the update() and decay()
methods change them over the configured update schedule. The code
decreases the one-to-many weight toward 0.1 and increases the
one-to-one weight toward 0.9.

The one-to-many branch permits multiple predictions to be assigned to
a ground-truth object during training. The one-to-one branch uses a
more restrictive assignment intended to support end-to-end detection.
The tal_topk arguments configure top-k settings used by the task-aligned
assignment logic; they are not the number of object classes.

This investigation identified the E2ELoss wrapper and how it combines
the two branches. It did not fully derive every lower-level formula
inside v8DetectionLoss, so detailed box-regression, classification,
and assignment calculations remain a possible deeper investigation.

============================================================
9. OVERALL MODEL FLOW
============================================================

The inspected model and training criterion can be summarized as:

    Input image
        |
        v
    Backbone extracts visual features
        |
        v
    Neck combines feature maps at multiple resolutions
        |
        v
    Detection head predicts box and class outputs
        |
        v
    During training, predictions are compared with ground truth
        |
        v
    One-to-many loss + one-to-one loss
        |
        v
    Weighted total loss
        |
        v
    Backpropagation and parameter updates during training

The final stages describe the training process conceptually. The
checkpoint inspection itself did not run a training session or measure
training convergence.

============================================================
10. CONCLUSION
============================================================

This exploration demonstrated how to inspect a pretrained object-
detection model rather than treating it as a black box. The investigation
identified the main layer types, traced feature-map shapes and layer
connections, inspected learned weights and BatchNorm values, interpreted
the detection head's output dimensions, and traced the model's criterion
to E2ELoss.

The most important findings were:

- The input tensor used for tracing was [1, 3, 640, 640].
- The model contained 2,572,280 parameters.
- The detection head used three scales with strides 8, 16, and 32.
- The main output tensor was [1, 84, 8400].
- The inspected criterion was E2ELoss, combining one-to-many and
  one-to-one loss branches with weights that change during training.
- The printed training hyperparameters were Ultralytics defaults and
  were not verified as the checkpoint's original training settings.

The exploration established a practical understanding of the model's
structure, tensor flow, parameter values, prediction head, and high-level
loss organization. A deeper follow-up could inspect the complete
v8DetectionLoss calculations or conduct controlled inference and training
experiments, if required.
